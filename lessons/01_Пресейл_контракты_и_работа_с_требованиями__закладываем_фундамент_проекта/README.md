# Домашнее задание

## «Выбор контрактной модели и отработка рисков для AI-проекта»

---

## 1. Исходная гипотеза заказчика

**Гипотеза:** заказчик хочет автоматизировать два взаимосвязанных процесса:

1. **Проверка обоснованности брошенных поездов (Причина 01)** — проверка юридической и фактической обоснованности временного отставления грузового поезда от движения.
2. **Претензионная работа (Проверка комплектности)** — проверка комплектности и юридической силы пакета документов по перечню 765/р для направления претензии и иска в суд.

**Ожидаемый результат:** система сама разбирает пакет документов, определяет нужный процесс, проверяет наличие и связность документов и выдаёт вердикт: «Готов к претензии» / «Готов с рисками» / «Не готов», а также готовит проект претензии для юриста.

**Ожидаемый эффект:** сокращение ручной проверки, ускорение подготовки претензий, снижение числа пропущенных ошибок, единая логика проверки.

## 2. Анализ: где здесь действительно ИИ, а где детерминированная разработка

### 2.1. Вывод

Проект **преимущественно детерминированный**: это система проверки документов и бизнес-правил. ИИ здесь — **вспомогательный слой распознавания и извлечения данных**, а не «мозг», который выносит юридический вердикт.

**Правильная архитектура:** детерминированное ядро проверок + AI-слой извлечения данных + human-in-the-loop для юриста.

**Неправильная архитектура:** «LLM читает всё и сама решает, виновен ли клиент». Для юридического процесса это неаудируемо и рискованно.

### 2.2. Детерминированные части (большинство системы)

Это правила, которые кодируются однозначно:

| Блок | Что проверяется |
|---|---|
| Маршрутизация | Есть ли Накопительная ведомость ФДУ-92 → процесс претензионной работы; нет → процесс брошения |
| Отсев смешанных пакетов | Справки 172/275 + ведомость одновременно → ошибка |
| Проверка срока доставки | Дата срока доставки vs дата фактического прибытия |
| Чек-лист комплектности | Наличие 21 документа Эталонного комплекта |
| Хронология | Акт на станции назначения → обращение ДС → приказ на бросание → акт на станции бросания |
| Связность | Номера поезда, приказа, обращения, акта, памятки, договора, вагона |
| Сроки действия | Договоры на эксплуатацию, ЭОД, соглашение о расчётах |
| Дубликаты и петли | Одинаковые реквизиты; АОФ, ссылающийся сам на себя |
| Расчёты | Количество вагонов и часов; сумма по Приказу 127-т/1 |
| Вердикт | По формальным правилам: «Готов» / «Не готов» / «Требуется ручная проверка» |

Это **не AI**, а rule engine / workflow / интеграции / проверки данных.

### 2.3. Где ИИ реально нужен

| AI-задача | Почему нужен ИИ |
|---|---|
| OCR / распознавание сканов | Акты ГУ-23, памятки ГУ-45, накладные, приказы, скриншоты извещений приходят как изображения |
| Классификация подвида АОФ ГУ-23 | В старых актах (2024–2025 гг.) подвид определяется только из описательной части текста |
| Извлечение сущностей | Номера документов, даты, станции, индексы поездов, номера вагонов, суммы, ссылки на договоры |
| Разбор таблиц | «Анализ занятости пути» и «Анализ переданных вагонов» в Excel/PDF/сканах |
| Поиск рискованных формулировок | Например, вывод «установлена вина ОАО "РЖД"» — как сигнал юристу, не как решение |
| Черновик претензии | Заполнение шаблона; юридически значимый текст остаётся шаблонным и проверяемым |

### 2.4. Почему проект нельзя оценивать как «чистый AI R&D» и нельзя как обычный FP

- **Не чистый AI R&D:** большая часть системы детерминирована и оцениваема.
- **Не обычный FP:** качество OCR, классификации старых актов и разбора таблиц на реальных данных заранее неизвестно. В документах прямо зафиксированы риски **Data Inadequacy** и **Model Nonconvergence**.

## 3. Выбор контрактной модели

### 3.1. Итоговая рекомендация

| Этап | Контракт | Почему |
|---|---|---|
| **PoC** | **T&M with a Cap** | Высокая R&D-неопределённость: качество сканов, старые акты, таблицы, отсутствие разметки. Cap защищает заказчика, T&M оплачивает итерации |
| **MVP** | **Гибрид: FP на детерминированное ядро + T&M with a Cap на AI-извлечение** | Ядро можно детализировать и оценить; AI-слой зависит от качества данных |
| **Scale** | **Гибрид: FP на инфраструктуру/HA/API + T&M на мониторинг и дообучение** | Инфраструктура стабильна и оцениваема; новые документы и дрейф — нет |

**Если нужен один контракт на старт:** **T&M with a Cap**.

### 3.2. Обоснование по этапам

#### PoC — T&M with a Cap

**Почему не FP:**

- На старте нет полного понимания качества данных.
- Риски **Data Inadequacy** (нет сырых логов/разметки) и **Model Nonconvergence** (на старых актах классификатор не достигает точности).
- Неизвестно, сколько итераций займёт OCR, классификация подвидов ГУ-23 и разбор таблиц.
- FP означал бы, что исполнитель берёт на себя риск, который невозможно оценить до Data Audit.

**Почему не чистый T&M:**

- Заказчик не должен получить открытый бюджет на исследования.
- Cap ограничивает верхнюю границу.

**Состав PoC (3–4 недели):**

- Data Audit Report: какие документы есть, в каком виде, сколько сканов, есть ли эталонная разметка;
- проверка OCR/извлечения на Golden Set;
- метрики: точность классификации подвида АОФ, recall извлечения ключевых полей, доля корректно разобранных таблиц;
- ADR интеграции: как AI-слой встраивается в детерминированное ядро;
- Go/No-Go Gate перед MVP.

**Критерий успеха PoC:** точность определения подвида АОФ и извлечения обязательных реквизитов не ниже согласованного порога на Golden Set; доля документов, требующих ручной проверки, приемлема. Если порог не достигнут — No-Go или пересмотр гипотезы.

#### MVP — гибридная модель

После PoC часть системы становится понятной:

- **FP на детерминированные блоки:** маршрутизация, чек-лист 21 документа, проверка дат, хронологии, дубликатов, петель, сроков договоров, расчёт суммы, API/UI, интеграции с АС ЭТРАН/ЕАСАПР. Скоуп детализируется через HLD/LLD и sizing.
- **T&M with a Cap на AI-слой:** OCR, классификация старых актов, извлечение сущностей, разбор таблиц, поиск рискованных формулировок.

**Почему не весь MVP по FP:** если заказчик после первой демо попросит новые модальности (скриншоты, новые формы актов, Excel), это классический **Scope Creep**. FP на всё сделает проект убыточным для исполнителя.

**Почему не весь MVP по T&M:** детерминированное ядро уже можно оценить достаточно точно, и заказчику выгоднее зафиксировать цену на эту часть.

**Метрики MVP:**

- precision/recall извлечения обязательных реквизитов;
- доля пакетов, автоматически доведённых до вердикта без ручной проверки;
- доля ложных «Готов к претензии» — критическая метрика, близка к нулю;
- Latency p95;
- доля ответов, проходящих guardrails;
- режим shadow mode: система проверяет реальные пакеты параллельно с юристом.

#### Scale — гибрид

- **FP:** HA-кластер, резервирование, RTO/RPO, API, наблюдаемость, runbook, дежурства, интеграции.
- **T&M:** мониторинг дрейфа, дообучение OCR/классификатора, новые формы документов, расширение на новые регионы/станции, разбор новых частных случаев.

**ADR на Scale:** зафиксировать, что AI-слой не выносит юридический вердикт; решение принимает детерминированное ядро + юрист. Зафиксировать возможность замены модели/провайдера LLM, требования к хранению ПДн на территории РФ, аудит-трейл.

## 4. Отработка рисков и возражений заказчика

### 4.1. Заказчик хочет все контракты привести к FP

**Что реально произойдёт:** FP означает, что весь риск оценки — на исполнителе. В AI-проекте это риск, который нельзя посчитать до Data Audit. Исполнитель сделает одно из трёх:

1. Заложит риск-премию 30–50% сверху — заказчик заплатит больше, чем при T&M with a Cap.
2. Откажется от проекта или сузит скоуп до безопасного минимума.
3. Согласится, но срежет качество: меньше итераций, слабее тестирование, экономия на Golden Set.

| Возражение заказчика | Ответ |
|---|---|
| «Мы хотим фиксированный бюджет, T&M — это открытый чек» | FP тоже не бесплатен: риск-премия закладывается в цену. T&M with a Cap даёт потолок (Cap) без наценки за неопределённость |
| «Скоуп уже понятен из документов 00 и 05» | Скоуп бизнес-логики понятен. Скоуп AI-слоя — нет: качество сканов старых актов, точность определения подвида ГУ-23, разбор таблиц. Это прямо записано в рисках: Data Inadequacy и Model Nonconvergence |
| «Мы уже делали ИТ-проекты по FP» | В классическом ИТ бизнес-логика детерминирована. Здесь качество зависит от распределения данных и стохастичности моделей. FP на R&D — это FP на исследование: либо дорого, либо плохо |
| «Давайте всё по FP, а если что — оформим Change Request» | Тогда FP теряет смысл: вы всё равно вернётесь к переговорам по каждому изменению. В AI-проекте изменения неизбежны, потому что вы учитесь по ходу |
| «Исполнитель просто хочет снять с себя риск» | Нет: T&M with a Cap перекладывает на исполнителя потолок (Cap ≈ 15–20%). Если исполнитель выходит за Cap — это его проблема. Заказчик защищён |

**Компромисс:** «FP после PoC». Сделать PoC по T&M with a Cap (3–4 недели), снизить неопределённость, после Go/No-Go перевести детерминированное ядро в FP, AI-слой оставить в T&M with a Cap.

**Что зафиксировать в договоре:**

- Cap на R&D-часть; выход за Cap — зона ответственности исполнителя;
- реестр рисков с AI-триггерами;
- порог Scope Creep и регламент Change Request;
- Stage Gate: без Go/No-Go после PoC MVP не начинается.

### 4.2. Заказчик хочет пропустить PoC

**Что реально произойдёт:** без PoC вы не знаете:

- есть ли пригодные данные и разметка (Data Audit не проведён);
- тянет ли OCR старые акты 2024–2025 и скриншоты извещений;
- можно ли надёжно определить подвид ГУ-23 из описательной части текста;
- парсятся ли таблицы «Анализ занятости» и «Анализ переданных вагонов»;
- каков baseline качества и есть ли смысл строить AI-слой.

Если сразу идти в MVP, вы строите на предположениях. Когда они не подтвердятся — переделка за свой счёт или спор о том, кто виноват.

| Возражение | Ответ |
|---|---|
| «Мы уже знаем, что хотим, PoC — потеря времени» | PoC — это не демо, а проверка данных и достижимости метрик. В эталонных DoD для PoC заложены Faithfulness ≥ 0,90, Context Precision ≥ 0,85 на Golden Set ≥ 500 кейсов. Без PoC эти цифры неоткуда взять |
| «3–4 недели — долго, давайте сразу MVP» | PoC дешевле, чем переделка MVP. Если данные непригодны, вы узнаете это за 3–4 недели, а не через 2 месяца разработки |
| «Покажите демо, и хватит» | Демо на 10 красивых документах не равно качеству на реальном потоке старых актов и скриншотов. Нужен Golden Set и Data Audit Report |
| «Мы подпишем ADR и без PoC» | ADR без данных — это решение на предположениях. ADR интеграции должен опираться на результаты PoC |

**Что теряет заказчик без PoC:** нет Data Audit Report; нет baseline метрик; нет Go/No-Go Gate; нет ADR интеграции; нет sizing.

**Компромисс:** «Сокращённый PoC» — 2 недели, только Data Audit + проверка OCR/классификации АОФ на 100–200 реальных документах. Если качество приемлемо — сразу MVP. Если нет — вы сэкономили месяцы.

### 4.3. Заказчик хочет пропустить MVP

**Что реально произойдёт:** PoC проверяет на Golden Set офлайн. MVP проверяет на реальном трафике онлайн:

- PoC не проверяет нагрузку, latency под нагрузкой, поведение на всём разнообразии реальных пакетов;
- PoC не проверяет guardrails на реальных данных;
- PoC не даёт статистически значимого подтверждения эффекта (p<0,05);
- PoC не проверяет интеграцию с АС ЭТРАН/ЕАСАПР в боевом режиме;
- PoC не проверяет, доверяют ли юристы системе.

Если прыгнуть из PoC сразу в Production — ошибки ударят по реальному юридическому процессу: неверные вердикты, проигранные суды, репутационные потери.

| Возражение | Ответ |
|---|---|
| «PoC работает, зачем MVP?» | PoC работает на эталонном наборе. MVP работает на реальном трафике. В DoD для MVP заложены: A/B-тест на 5–10% трафика ≥ 2 недель, p<0,05, Latency p95 < 200 мс, ≥ 90% ответов проходят guardrails, дашборды наблюдаемости |
| «Давайте сразу в прод, там и потестим» | В юридическом процессе «потестим в проде» = риск неверных претензий и исков. Нужен shadow mode: система работает параллельно с юристом, вердикт пока не влияет на процесс |
| «MVP — это просто демо» | MVP — не демо, а доказательство эффекта на ограниченном трафике с измеримыми метриками. Production без MVP — «большой взрыв»: если что-то пойдёт не так, откатываться некуда |
| «Нам нужно быстро» | MVP 6–8 недель быстрее, чем аварийный откат из продакшена и разбор юридических последствий |

**Что теряет заказчик без MVP:** нет A/B-теста; нет проверки guardrails на реальных данных; нет наблюдаемости; нет shadow mode; нет статистической значимости.

**Компромисс:** «MVP в режиме shadow mode на 5% трафика, 2 недели». Система работает параллельно с юристом, вердикт не влияет на процесс. Минимальный риск и максимальная доказательность.

### 4.4. Заказчик хочет пропустить и PoC, и MVP — сразу в Production

**Что реально произойдёт:** худший сценарий — весь бюджет ставится на непроверенные предположения. Классический «big bang»:

- нет Data Audit → можете узнать посреди проекта, что данных/разметки нет;
- нет baseline → нечего сравнивать, эффект не доказан;
- нет Go/No-Go → негде остановиться;
- нет shadow mode → юристы не доверяют системе;
- ошибки сразу попадают в реальный юридический процесс.

В документах заказчика записаны три классических риска AI-проекта: **Scope Creep**, **Data Inadequacy**, **Model Nonconvergence**. Все три смягчаются именно поэтапным подходом.

| Возражение | Ответ |
|---|---|
| «Agile же, зачем этапы?» | Agile — это итерации внутри этапа, а не отказ от проверки гипотез. Stage Gate (Go/No-Go) — это не водопад, а точки принятия решений |
| «Нам нужен результат быстро» | Самый быстрый путь к результату — не сэкономить 3–4 недели на PoC, а не потерять 2–3 месяца на переделку |
| «Мы готовы рискнуть» | Риск можно принять, но его нужно оценить. Score = Probability × Impact. Без PoC/MVP вы принимаете риск, который не измерили. Это не риск-менеджмент, а ставка |
| «Мы сами будем тестировать в проде» | Тогда зафиксируйте это письменно: кто отвечает за неверные вердикты, кто несёт юридические последствия, какие есть guardrails. Без этого ответственность размыта |

**Что предложить вместо — минимальная последовательность, от которой нельзя отказываться:**

1. **Data Audit (1–2 недели)** — есть ли данные, разметка, качество сканов.
2. **PoC (3–4 недели)** — проверка достижимости метрик на Golden Set + ADR + Go/No-Go.
3. **MVP в shadow mode (6–8 недель)** — A/B на 5–10% трафика, guardrails, наблюдаемость.
4. **Production** — HA, RTO/RPO, runbook, дежурства, retraining.

Если заказчик категорически не хочет полный PoC — предложить **сокращённый Data Audit + PoC на 100–200 документах**.

## 5. Сводная таблица рисков

| Что хочет заказчик | Главный риск | Вероятность | Влияние | Score | Что делать |
|---|---|---|---|---|---|
| Всё в FP | Риск-премия 30–50% или срез качества | Высокая | Высокое | ≥ 16 | FP только на детерминированное ядро после PoC; AI — T&M with Cap |
| Пропустить PoC | Строительство на непроверенных данных | Высокая | Высокое | ≥ 16 | Минимум Data Audit + сокращённый PoC |
| Пропустить MVP | Ошибки сразу в юридическом процессе | Средняя | Очень высокое | ≥ 16 | Shadow mode на 5% трафика, 2 недели |
| Пропустить PoC и MVP | «Big bang»: весь бюджет на ставку | Средняя | Критическое | 20–25 | Письменно зафиксировать ответственность; минимум Data Audit |

**Формула:** Score риска = Probability (1..5) × Impact (1..5). Score ≥ 16 — Critical/High, требует превентивного плана до подписания контракта.

## 6. Как вести разговор с заказчиком

1. **Не говорите «нет»** — говорите «да, и вот что нужно, чтобы FP/прыжок сработали».
2. **Покажите математику:** риск-премия FP vs Cap; стоимость переделки vs стоимость PoC.
3. **Опирайтесь на документы заказчика:** в его же эталонных DoD уже заложены метрики PoC и MVP. Вы не придумываете этапы — вы следуете его же регламенту.
4. **Предложите выбор:** «Полный PoC 3–4 недели или сокращённый 1–2 недели». Это переводит разговор из «делать/не делать» в «какой формат».
5. **Зафиксируйте письменно:** если заказчик принимает риск, это должно быть в реестре рисков с подписью, а не в устной договорённости.

|---|---|
| **FP** | Fixed Price, фиксированная цена |

| **Cap** | Потолок бюджета в T&M with a Cap |
| **PoC** | Proof of Concept, доказательство концепции |
| **MVP** | Minimum Viable Product, минимально жизнеспособная версия |

| **ADR** | Architecture Decision Record, запись архитектурного решения |
| **Go/No-Go Gate** | Контрольная точка «продолжать/остановить» |
| **Scope Creep** | Расползание объёма работ |
| **Change Request** | Формальный запрос на изменение |
| **Shadow mode** | Система работает параллельно с человеком, но не влияет на процесс |
| **Guardrails** | Защитные фильтры для модели |
| **A/B-тест** | Сравнение двух вариантов на трафике |
| **p<0,05** | Статистическая значимость результата |
| **Latency p95** | Задержка, в которую укладываются 95% запросов |

## 9. Итоговый вывод для защиты работы

1. **Проект преимущественно детерминированный.** ИИ здесь — слой распознавания и извлечения, а не источник юридического вердикта.
2. **Чистый FP на старте неприменим** из-за R&D-неопределённости: качество OCR, старые акты, таблицы, отсутствие разметки.
3. **Рекомендуемая модель:**
   - **PoC — T&M with a Cap;**
   - **MVP — гибрид FP (ядро) + T&M with a Cap (AI);**
   - **Scale — гибрид FP (инфраструктура) + T&M (мониторинг и дообучение).**
4. **Прыжок через этапы — главный риск.** PoC и MVP снимают неопределённость, которую нельзя снять иначе. Без них проект превращается в ставку.
5. **Ответ заказчику:** «FP — да, но после PoC и только на детерминированное ядро; AI-слой — T&M with a Cap; этапы обязательны, но их формат можно сократить».
